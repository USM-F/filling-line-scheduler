# Filling-Line Scheduler

## Запуск приложения

Нужны Linux/WSL, Bash и Docker. Python 3.11 и зависимости устанавливаются в контейнере.

```bash
./scripts/build.sh
./scripts/run.sh inspect \
  --input test/data/filling_only_20_product_assignment_input.json \
  --report output/inspection.json --debug
```

`inspect` проверяет входную схему и выводит JSON-сводку. Логи записываются в stderr
и `.logs/`. `--force` разрешает перезапись отчёта и пересоздаёт venv;
`./scripts/build.sh --force` также пересобирает Docker image.

Рабочий каталог монтируется в контейнер по тому же пути; аргументы передаются без
изменений. По умолчанию это текущий каталог. Для внешних данных задайте
`FLS_WORK_DIR=/путь/к/данным`. Окружение хранится в `.venv` проекта.

## Запуск тестов

```bash
./scripts/run_tests.sh
./scripts/run_tests.sh -k test_base_input
./scripts/run_tests.sh --smoke
```

Python-тесты находятся в `test/`, данные — в `test/data/`,
отчёт покрытия — в `.cache/coverage.xml`.
Docker smoke проверяет подготовку и повторное использование окружения, `--force`
и запуск без сети.

## Описание модели

Входной JSON задаёт недельный спрос, совместимость продуктов и линий,
производительность, смены с перерывами и матрицу переналадок.

Математическая постановка — единая event-based MILP с backend HiGHS:
каждый продукт целиком назначается одной совместимой линии; модель выбирает порядок
продуктов и время производства с учётом календаря. Производство останавливается на
перерывах, переналадки могут выполняться и в нерабочее время. Первый продукт на линии
не требует переналадки; возвраты A–B–A и разделение продукта между линиями запрещены.

Цели по приоритету: минимальное суммарное время переналадок, затем минимальное время
завершения и наиболее ранние старты. Формат расписания — упорядоченные по линиям
слоты `production` и `changeover` с ISO 8601 временем в часовом поясе входных данных.

Пример в `test/data/`: 20 продуктов, 13 линий, 84 допустимые пары,
спрос 1 133 892 единицы, часовой пояс `Asia/Bangkok`, точность 1 минута.
