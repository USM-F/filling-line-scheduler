# MILP-модель разлива с разделением объёма между линиями

## Назначение и допущения

[Исходная постановка](filling_only_20_product_assignment.md) задаёт спрос,
совместимость SKU и линий, производительность, общий календарь и направленную
матрицу переналадок. Монолитная MILP решается HiGHS через `highspy`.

- Объём каждого активного SKU можно распределять между совместимыми линиями,
  в том числе выпускать одновременно. На одной линии SKU образует один смысловой run.
- Количества целые. Время отсчитывается целыми ticks от начала горизонта;
  один tick равен `precisionMinutes` минутам. Рабочие окна и переналадки кратны tick.
- Производительность постоянна для пары SKU–линия и даёт целое положительное
  число единиц за tick. Неподдерживаемую скорость отклоняем, а не округляем.
- Run непрерывен в производительном времени: в обед и между сменами он
  приостанавливается и затем продолжается. Эти паузы не считаются фрагментацией.
- Переналадки занимают календарное время, могут выполняться в нерабочее время
  и не требуют общего межлинейного ресурса. Первый run на линии бесплатен.
- Нет минимальных партий, складских ограничений, сроков отдельных SKU,
  ограничений работников или предшествования между линиями.
- SKU с нулевым спросом не создают переменных и слотов. В summary их количество равно нулю.

## Подготовка данных и календаря

Схема Pydantic запрещает неизвестные поля, неявное приведение типов и отрицательные
величины. Загрузчик сохраняет десятичные скорости как `Decimal`, обнаруживает
повторяющиеся JSON-ключи и сообщает путь ошибки. Семантическая подготовка дополнительно
проверяет уникальность идентификаторов, ссылки eligibility, покрытие линий календарём,
полноту матрицы, её нулевую диагональ, смены, перерывы и временную сетку.

Дата рабочего дня — дата начала смены. Субботняя ночная смена продолжается в воскресенье,
даже если воскресенье не входит в `workingDays`. Перерывы могут пересекать полночь;
`startsNextDay` относится к дате начала смены. Сначала строятся смены с предыдущей
локальной даты до конца горизонта, затем вычитаются перерывы и результат обрезается
горизонтом. Соприкасающиеся рабочие интервалы объединяются. Пересекающиеся смены
или перерывы отклоняются. Границы с неоднозначным или несуществующим локальным
временем при переходе DST отклоняются; длительности считаются в UTC.

Получаются непересекающиеся окна \([a_k,b_k)\) в ticks и накопленное рабочее время
\(F_k=\sum_{h<k}(b_h-a_h)\). Начало производства может совпадать с началом окна,
окончание — с его правой границей. Начинать run на правой границе окна нельзя.
`inspect` проверяет только входную схему, но не эти семантические условия и не выполнимость.

## Параметры и переменные

Обозначения: \(I\) — активные SKU, \(L\) — линии, \(E\subseteq I\times L\) —
допустимые пары, \(D_i\) — спрос, \(T\) — длина горизонта в ticks,
\(H=\sum_k(b_k-a_k)\) — доступное производительное время.

\[
U_{i\ell}=r_{i\ell}\,\Delta/60\in\mathbb Z_{>0},\qquad
C_{ij}=\operatorname{changeoverMinutes}_{ij}/\Delta\in\mathbb Z_{\ge0}.
\]

Здесь \(r\) измеряется в единицах/час, \(\Delta\) — минут/tick.

| Переменная | Область | Смысл |
| --- | --- | --- |
| \(y_{i\ell}\) | binary | Назначение SKU на линию |
| \(q_{i\ell}\) | integer ≥ 0 | Объём на линии |
| \(p_{i\ell}\) | integer ≥ 0 | Производительная длительность |
| \(s_{i\ell},c_{i\ell}\) | integer, [0,T] | Календарные начало и окончание |
| \(f_{i\ell},t_{i\ell}\) | binary | Первый и последний run |
| \(x_{ij\ell}\) | binary | Непосредственное следование j за i |
| \(v_\ell\) | binary | Линия используется |
| \(z^s_{i\ell k},z^c_{i\ell k}\) | binary | Окна начала и окончания |
| \(\sigma_{i\ell k},\kappa_{i\ell k}\) | continuous ≥ 0 | Смещения внутри выбранных окон |
| \(M\) | integer, [0,T] | Makespan |

Дуги существуют только между различными совместимыми SKU на одной линии.

## Объёмы и точное округление длительности

\[
\sum_{\ell:(i,\ell)\in E}q_{i\ell}=D_i,\qquad
 y_{i\ell}\le q_{i\ell}\le D_i y_{i\ell}.
\]

Пусть \(P^{max}_{i\ell}=\min(\lceil D_i/U_{i\ell}\rceil,H)\).

\[
q_{i\ell}\le U_{i\ell}p_{i\ell},\qquad
q_{i\ell}\ge U_{i\ell}(p_{i\ell}-y_{i\ell})+y_{i\ell},\qquad
0\le p_{i\ell}\le P^{max}_{i\ell}y_{i\ell}.
\]

При \(y=1\): \(U(p-1)+1\le q\le Up\), поэтому точно
\(p=\lceil q/U\rceil\). При \(y=0\) получаем \(p=q=0\).
Верхняя граница q дополнительно ограничена \(\min(D_i,U_{i\ell}H)\).
Пара сохраняется, даже если полный спрос на линии не помещается: часть объёма может поместиться.
Только последний tick run может быть неполным.

## Путь и переналадки

Для каждого назначения:

\[
f_{i\ell}+\sum_{j\ne i}x_{ji\ell}=y_{i\ell},\qquad
t_{i\ell}+\sum_{j\ne i}x_{ij\ell}=y_{i\ell}.
\]

Для линии: \(\sum_i f_{i\ell}=v_\ell\), \(\sum_i t_{i\ell}=v_\ell\).

\[
c_{i\ell}\ge s_{i\ell}+p_{i\ell},\qquad
s_{j\ell}\ge c_{i\ell}+C_{ij}-(T+C_{ij})(1-x_{ij\ell}).
\]

При невыбранной дуге правая часть не больше нуля, поскольку \(c\le T\).
При выбранной дуге следующий run начинается после окончания предыдущего и переналадки.

Цикл невозможен: сумма временных ограничений вдоль цикла требует, чтобы время начала
было не меньше самого себя плюс сумма положительных \(p\) и неотрицательных \(C\).
Каждый выбранный run имеет \(q\ge1\), следовательно \(p\ge1\).
Баланс входящих и исходящих дуг вместе с отсутствием циклов даёт один путь на используемой
линии. Дополнительные MTZ-rank переменные не нужны. Один узел на пару SKU–линия
исключает A–B–A на линии при разрешённом split между линиями.

## Календарная линеаризация

Для каждой пары (индексы пары ниже опущены), \(h_k=b_k-a_k\):

\[
\sum_k z^s_k=\sum_k z^c_k=y,\quad
0\le\sigma_k\le(h_k-1)z^s_k,\quad
z^c_k\le\kappa_k\le h_kz^c_k.
\]

\[
s=\sum_k(a_kz^s_k+\sigma_k),\qquad
c=\sum_k(a_kz^c_k+\kappa_k),
\]

\[
p=\sum_k(F_kz^c_k+\kappa_k)-\sum_k(F_kz^s_k+\sigma_k).
\]

У выбранного назначения ровно по одному окну начала и окончания. Смещения непрерывные,
но равенства с целыми s/c и целыми границами окон вынуждают выбранные смещения быть целыми.
У невыбранного назначения все оконные переменные, s/c/p равны нулю.

Разность накопленного рабочего времени исключает обеды и межсменные промежутки из p,
а разность c−s включает их в календарную длительность. Поэтому run может пересекать
сколько угодно перерывов без бинарных переменных на каждую минуту. Размер календарной
части модели пропорционален числу допустимых пар × числу рабочих окон.

## Четыре лексикографические цели и лимит

1. \(\min\sum_{ij\ell}C_{ij}x_{ij\ell}\) — переналадки.
2. \(\min\operatorname{splitExcess}=\sum_{i\ell}y_{i\ell}-|I|\) — дополнительные назначения.
3. \(\min M\), где \(M\ge c_{i\ell}\) — окончание расписания.
4. \(\min\sum_{i\ell}s_{i\ell}\) — ранние старты.

После доказательства оптимума значение цели фиксируется равенством. Только затем
запускается следующий проход. Все цели целочисленные; достаточное доказательство —
округлённая вверх нижняя граница HiGHS достигает целого значения incumbent
(с численным допуском 1e−6). Ненулевой запрошенный gap не разрешает переходить
к следующей цели без такого доказательства. Gap HiGHS для второго прохода относится
к числу назначений до вычитания константы |I|; value и bound в metrics уже содержат вычет.

По умолчанию: один поток, seed 0, относительный и абсолютный gap 0,
300 секунд на общий цикл подготовки native-модели и solver-проходов.
Перед каждым проходом передаётся оставшееся время, предыдущий incumbent используется
как начальное решение. Небольшое превышение wall time возможно при остановке HiGHS.
Извлечение, проверка и публикация не входят в solver-бюджет.

`OPTIMAL` означает доказанность всех четырёх целей. `FEASIBLE` означает проверенный
incumbent при недоказанной оптимальности хотя бы одной цели. Он сохраняется и возвращает
код 0. Без incumbent — код 4, при доказанной невыполнимости — 3. Ошибки входа — 2,
ошибки независимой проверки — 7, артефактов — 8, неожиданные внутренние ошибки — 9.
Коды 1, 5 и 6 сохранены в enum для совместимости и будущих этапов.

## Извлечение, JSON и независимая проверка

Каждый run пересекается с рабочими окнами и становится последовательностью физических
`production`-слотов. Все слоты, кроме последнего в run, выпускают полный объём
`длительность × U`. Последний получает остаток. Переналадка размещается сразу после
предыдущего run и до следующего; паузы явно слотами не записываются.

JSON сохраняет [контракт постановки](filling_only_20_product_assignment.md#output):
`scheduleId`, `timeZone`, массив `lines` с `production`/`changeover` и `summary`.
Включаются все линии, в том числе пустые. `productsSplitAcrossMultipleLines` — число SKU
с положительным выпуском на нескольких линиях. Это отличается от `splitExcess`:
один SKU на трёх линиях даёт соответственно 1 и 2.

Валидатор работает только с подготовленными входными данными и физическими слотами;
он не импортирует MILP или HiGHS. Он независимо пересчитывает спрос по всем линиям,
проверяет eligibility, точность количества и последнего tick, сетку, часовой пояс,
границы горизонта, календарь, порядок и пересечения, паузы внутри run, A–B–A,
полноту и длительности переналадок, все поля summary. Он подтверждает допустимость,
но не оптимальность. Календарная подготовка общая с solver; в синтетических тестах
её дополняет независимая пошаговая календарная симуляция и перебор объёмов/порядков.

`validate` выводит JSON с `valid`, `errors` (машинный code, path, message) и
пересчитанной summary. Структурно некорректный JSON даёт код 2, допустимый по схеме,
но неверный по ограничениям — JSON-отчёт и код 7.

`solve` формирует `schedule.json`, `schedule.html`, `schedule.metrics.json`.
Путь HTML можно задать `--html-output`. Metrics содержит четыре достигнутые цели,
статусы/границы/gap каждого запущенного прохода, размер модели, настройки, версии,
времена и путь журнала HiGHS. Диагностика приложения — stderr и `.logs/<run_id>.jsonl`,
native-журнал — `.logs/<run_id>.highs.log`; вывод HiGHS не попадает в stdout.

После независимой проверки полностью формируются JSON, HTML и metrics. Затем все
три файла записываются во временные файлы, публикуются metrics и HTML, последним JSON.
Без `--force` перезапись запрещена; проверяются совпадения путей и aliases с входом.
Ошибка renderer не изменяет существующие результаты. Каждый файл публикуется атомарно,
но вся тройка не является транзакцией файловой системы: ошибка между публикациями
может оставить часть новых сопровождающих файлов. JSON выступает последним маркером
публикации; такой сбой возвращает 8. При неудаче solver остаются журналы диагностики,
новое расписание не публикуется.

## Чтение HTML Gantt

HTML автономен: CSS и SVG встроены, CDN, JavaScript и сетевые запросы отсутствуют.
Одна строка соответствует одной линии, ось идёт от первого до последнего слота
и подписана в часовом поясе расписания. Цвет SKU стабилен между линиями и файлами;
переналадки серые со штриховкой. Наведение показывает продукт или переход,
точные начало/окончание, длительность и количество. Паузы видны промежутками.
Широкая диаграмма прокручивается горизонтально. Наверху — итоговые количества,
минуты переналадок и число разделённых SKU, внизу — легенда.

Все пользовательские строки экранируются. Самостоятельный `render` читает только
JSON и не утверждает, что он прошёл независимую проверку; для этого нужен `validate`.

## Проверки и фактический baseline

Обычный набор тестов исключает маркер `baseline`; CI запускает его отдельным шагом
и сохраняет JSON, HTML, metrics и журналы в диагностических артефактах.

Синтетические oracle: вынужденный split 150 на двух линиях по 100 ticks даёт 75/75
и makespan 75; необязательный split спроса 80 не используется; спрос 250 на трёх
таких линиях даёт splitExcess 2. Календарный пример A=100, B=90, C=120, D=250
даёт 10 минут переналадок, отсутствие split и окончание в 01:40.
Малые случаи сопоставляются с полным перебором целочисленных объёмов, порядков
и независимой симуляцией рабочих минут. Есть проверки повреждённых расписаний,
ограничения времени с incumbent и без него, экранирования HTML и ошибок публикации.

Baseline: 20 активных SKU, 13 линий, 84 допустимые пары, спрос 1 133 892,
24 рабочих окна, 6840 производительных минут на линию. Нижняя граница переналадок —
210 минут: не менее 20 runs, не более 13 бесплатных первых runs, каждая
последующая переналадка не короче 30 минут. Это нижняя граница, а не заранее
заданный результат или ограничение split.

Запуск 5 сентября 2026 года через `./scripts/run_tests.sh -m baseline --no-cov`:
Python 3.11.15, HiGHS 1.11.0, Linux x86_64, один поток, seed 0, gap 0.
Модель: 9330 переменных (4961 бинарная, всего 5298 целочисленных), 7934 ограничения,
37 618 ненулевых коэффициентов, 664 дуги. Числа относятся к модели до presolve и
до добавления равенств фиксации целей.

| Проход | Достигнуто | Нижняя граница | Статус HiGHS | Время, с |
| --- | ---: | ---: | --- | ---: |
| Переналадки, минуты | 210 | 210 | Optimal | 4.697 |
| splitExcess | 0 | 0 | Optimal | 0.247 |
| Makespan, ticks | 1501 | 1501 | Optimal | 22.742 |
| Сумма стартов, ticks | 3908 | 649 | TimeLimit | 272.301 |

Общее solver-время — 300.029 с, до публикации с подготовкой, проверкой и HTML —
300.110 с. Выпущены все 1 133 892 единицы, создано 57 физических слотов, использованы
13 линий. Расписание заканчивается **2026-08-18 09:31:00 +07:00**.
Переналадки достигли нижней границы 210 минут. В этом решении разделённых SKU нет;
это полученный результат оптимизации, а не запрет split в модели или требование теста.

Оптимальность первых трёх целей доказана. Последняя имеет gap 83.393%; её оптимум
не доказан, поэтому общий статус — **FEASIBLE**. Он не означает недопустимость:
расписание прошло проверку внутри solve и отдельной командой validate.
Время и качество последнего прохода могут меняться с производительностью машины.

После запуска baseline результаты находятся в `output/`: [JSON](../output/baseline.json),
[HTML Gantt](../output/baseline.html), [metrics](../output/baseline.metrics.json).
Путь журнала HiGHS указан в поле `highs_log` файла metrics.
Артефакты генерируются локально и не хранятся в Git; в CI они доступны в диагностических артефактах.
